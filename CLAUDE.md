# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

MiniJava compiler for the Compiladores e Intérpretes course (UNS), built in stages: Etapa 1 lexer, Etapa 2 LL(1) recursive-descent parser with panic mode, Etapa 3 semantic analysis (declaration checking via a symbol table), Etapa 4 statement checking (Sem2: base rules of §9–§12 plus the Multi-detección, Postfijos, For, Instanceof, Visibilidad chequeada, Todos los caminos llevan al retorno sin código muerto, Atributos inicializados, Super! and Ternarios logros; the other logros are pending). Plain Java (no Maven/Gradle), JDK 21. Code, comments, identifiers and docs are in Spanish; keep it that way.

## Commands

All commands run from `Código/` — testers resolve case folders with relative paths like `resources/semantico/conErrores/`, so they fail from anywhere else.

```bash
./build.sh                                     # compiles src/Model, src/Controller, src/View into out/classes and builds out/compilador.jar (main: View.ModuloPrincipalET4)
java -jar out/compilador.jar <archivo-fuente>  # run lexer + parser + semantic checks on one file
./test.sh                                      # build + run every tester (Stages 1-3 and Sem2), one line each (failures listed); exit 1 if any fails
./test.sh etapas1-3                            # only the Stage 1-3 testers; `sem2` = only the Sem2 ones
```

The `.githooks/pre-commit` hook runs `./test.sh` on every commit that touches `Código/`. Enable it once per clone with `git config core.hooksPath .githooks`.

Test classes (package `test.java`): `TesterDeCasos{Sin,Con}Errores` (lexer), `TesterSintacticoDeCasos{Sin,Con}Errores` and `TesterSintacticoModoPanico` (parser), `TesterSemanticoDeCasos{Sin,Con}Errores` (semantic, declarations), `Tester{Sin,Con}ErroresSem2` and `TesterLogrosSem2` (semantic, statements: Sem2). To check a single case, run the jar directly on its file and compare against the file's first line.

## Architecture

Layered MVC under `Código/src/`:

- **View**: one entry point per stage, all kept working because the testers for each stage call them: `ModuloPrincipal` (lexer only, prints tokens), `ModuloPrincipalET2` (lexer + parser), `ModuloPrincipalET3` (lexer + parser + declaration checks, frozen), `ModuloPrincipalET4` (adds statement checking; the jar's main). View only handles presentation and output format.
- **Controller**: `Analizador*HandlerImpl` wires the pipeline for each stage. The ET3 wiring is in `AnalizadorSemanticoHandlerImpl`: `SourceManagerMejorado` → `AnalizadorLexicoImpl` → `AnalizadorSintacticoImpl(lexico, tablaSimbolos)` → `sintactico.start()` → `tablaSimbolos.estaBienDeclarado()` → `tablaSimbolos.consolidar()`. Both run even when there were syntax errors. `AnalizadorSemantico2HandlerImpl` (ET4) runs the same and then `tablaSimbolos.chequearSentencias()`, but only if there were no lexical, syntax or declaration errors.
- **Model/lexico**: hand-written automaton (one method per state) in `AnalizadorLexicoImpl`. The parser pulls tokens from it one at a time. Lexical errors are pushed to a `ResultadoLexicoListener` (the View), and analysis continues after them.
- **Model/sintactico**: `AnalizadorSintacticoImpl` is a recursive-descent LL(1) parser. Each method has the grammar production it implements in a comment above it. It recovers in panic mode (`sincronizar()`) and collects `ErrorSintactico`s instead of throwing. It also runs the semantic actions that build the symbol table while it parses (Pasada 1: register names; Pasada 2: inheritance, attributes, methods), calling the `TablaSimbolos` setters (`setClaseActual`, `setMetodoActual`, `agregarMetodoActualAClaseActual`, …).
- **Model/semantico**: `TablaSimbolos` is a single instance passed by reference (deliberately not a Singleton; see the docs). It stores `Clase`/`Interfaz` in one shared namespace (`LinkedHashMap`, so error order is deterministic) and collects all `ErrorSemantico`s. The checks run as two separate calls, and the order matters: (1) `TablaSimbolos.estaBienDeclarado()` runs `Chequeable.estaBienDeclarado(tabla, entornoGenerico)` on each entity as the user wrote it, delegating down to members and passing along the in-scope generic type params; (2) `TablaSimbolos.consolidar()` calls `Clase/Interfaz.consolidar()`, which resolves inheritance and cycles and copies parent members. Running (1) after (2) would report errors twice in subclasses. ET4 adds (3) `TablaSimbolos.chequearSentencias()`, the third pass over the bodies (see Sem2 below). `Tipo` is a single class (no primitive/reference hierarchy) with `conformaCon`, `Tipo.NULL` and `Tipo.VOID`; `Metodo` still uses `tipoRetorno == null` for `void`.

## Output format and test cases

Testers capture stdout and match tags, so the output format is a contract:
- Success: `[SinErrores]`
- Lexical/syntax error: a readable line, then `[Error:<lexema>|<línea>]`
- Semantic error: `Error Semántico en línea <L>: <descripción>`, then `[Error:<lexema>|<línea>]`. This is the same tag as lexical/syntax errors, as the course guidelines require. The lexeme is the name of the entity that triggers the error, and lexeme and line come from the same token. Internally each error has a fixed category code (`ERR_CLASE_DUPLICADA`, `ERR_HERENCIA_CICLICA`, …) that only picks the description (`ErrorSemantico.getDescripcion()`) and documents the cases. It is never printed in the tag (see `Documentación/etapa3-semantico/casos-de-prueba.md`).

Case files live in `Código/resources/{sinErrores,conErrores}` (lexer), `resources/sintactico/{sinErrores,conErrores,panico}` and `resources/semantico/{sinErrores,conErrores,multiError}` and `resources/semantico2/{sinErrores,conErrores}` (Sem2). Parameterized testers pick up every file in their folder. In error cases, the **first line** must be `///<expected tag>` (e.g. `///[Error:A1|5]`), and the test checks that the tag appears in the output. To add a case, drop a file in the folder; no code changes are needed. Panic-mode and `multiError` cases have hand-written assertions or are not covered by a tester.

## Sem2 (statement checking)

Implemented by spec 0003 (`Documentación/specs/0003-chequeo-sentencias-base.md`). The parser builds an AST (`Model.semantico.ast`, `Nodo*`) for every method body, constructor body and attribute initializer and hangs it on `Metodo`, `Constructor` and `Atributo`. The third pass, `TablaSimbolos.chequearSentencias()`, walks the classes in `LinkedHashMap` order (skipping interfaces and predefined types) and, in each one, only its **own** members: initialized attributes, constructors, methods. No cascade: it does not run at all if an earlier stage reported errors. Each statement is checked separately: a node throws `ExcepcionSemantica`, `NodoBloque` catches it per statement and records it, and checking goes on with the next statement (logro *Multi-detección*). Locals live in a block stack in `TablaSimbolos` (`abrirBloque`/`cerrarBloque`, `buscarVariable`: locals → parameters → attributes). Logro syntax the parser accepts (lambda, classic locals, array initializers, generic methods, diamond) has nodes, but checking them reports `ERR_NO_SOPORTADO`; the logros checked are postfix `++`/`--`, the ternary (see below), `for` (classic and for-each) `instanceof` (`NodoExpInstanceof`; `instanceof` is a keyword and a link of `<ExpresionCompuestaResto>`) and visibility (`private` is stored on `Atributo`/`Metodo`/`Constructor`; the six member accesses and `super(...)` (through `ChequeoLlamada.chequearConstructor()`) call `ChequeoVisibilidad.exigirAcceso()`, and Etapa 3 still copies private members to subclasses). The return-paths logro (spec 0004) is always on in ET4 and replaces the part of §12.5 that allowed missing returns and unreachable code (ADR 0008). Flow rules are structural (`NodoSentencia.salida(Flujo)`, states `VIVO`/`MUERTO`/`RECUPERANDO` like javac's `Liveness`, no types involved): a non-void method whose body ends `VIVO` gets `ERR_FALTA_RETORNO` on its name (`Metodo.exigirRetorno`, run before the body is checked, so type errors don't affect it). Unreachable statements are reported during type checking: `NodoBloque` records `ERR_SENTENCIA_INALCANZABLE` on the first token of a statement reached `MUERTO`, still checks it, and continues `RECUPERANDO`, so what follows isn't reported in cascade (unless that statement itself doesn't complete normally, e.g. another `return`). A statement that throws a type error before reaching its branches (`if (1) {...}`) doesn't look for unreachable code inside them (spec 0004, D5). Only the literal `true`/`false`, optionally parenthesized, is a constant condition (`NodoExpresion.valorConstante()`): no expression is evaluated, so `while (1 < 2)` is an ordinary loop, unlike Java (ADR 0009; folding was tried and dropped, kept on the local branch `respaldo/ticket03-plegado`). The semantic stages never evaluate expressions (no constant folding, not even of literal-only expressions like `1 > 9`): they check types, declarations, variable use and statement structure; a logro that would need a compile-time value in Java must be flagged and asked about first. Initialized attributes (spec 0005) are checked in their declaring class as an instance context: `Atributo.chequearInicializador` requires the initializer to conform to the attribute's type like the right side of `=` (else `ERR_ASIGNACION_INCOMPATIBLE` on the `=` token, which `Atributo` keeps). A bare name (`NodoAccesoVar`) inside an initializer that resolves to an attribute of the current class not declared strictly before the one being initialized (itself included) is `ERR_REFERENCIA_ADELANTADA` on the name (JLS §8.3.3); order comes from `Atributo.getIndiceDeclaracion()`, assigned by `Clase.agregarAtributo()`, not from the line or the `HashMap`. The direct target of `=` is exempt (`NodoExpAsignacion` calls `chequearComoDestino`), `this.b`, inherited attributes and what a called method reads don't count, and the rule doesn't apply in methods or constructors. `super` (spec 0006, logro *Super!*) is the keyword `PR_SUPER` with two forms: the super access (`super.x`, `super.m(...)`: `NodoSuper`, typed as `Clase.getTipoSuperclase()`, i.e. the `extends` as written or `Object`, then the usual chained checks; `ERR_SUPER_EN_ESTATICO` in a static context) and the statement `super(...);` (`NodoLlamadaSuperConstructor`), which is only valid as the literal first statement of a constructor (`Constructor.setCuerpo()` marks it; anywhere else `ERR_SUPER_FUERA_DE_LUGAR`), as in JDK 21 and not JDK 25 (ADR 0010). It resolves the superclass constructor like `new` (`ChequeoLlamada.chequearConstructor()`), with errors on `super`, and checks only its arguments with the pre-construction flag on (`TablaSimbolos.prenderContextoPrevioAConstruccion()`, restored to its previous value in a `finally`): `this`, a super access, a bare attribute or an unqualified instance method call there is `ERR_REFERENCIA_ANTES_DE_SUPER` on its token. Those four uses of the current object all go through `TablaSimbolos.exigirObjetoActual(token, codigoEstatico)`, which checks the static context first and then the flag. §6.3 still holds: no implicit `super()`. The ternary (spec 0007, logro *Ternarios*) is typed by its target where there is an expected type and by conformance between branches elsewhere (ADR 0011): `NodoExpresion.chequearConTipoEsperado(tabla, esperado)` defaults to `chequear(tabla)` (a `null` expected type means none, so each context makes a single call) and only `NodoExpTernaria` and `NodoExpParentizada` (without a chain) override it. The contexts with an expected type call it instead of `chequear`: `NodoExpAsignacion` (the target's type), `Atributo.chequearInicializador`, `NodoReturn` in a non-void method and `ChequeoLlamada.chequearArgumentos` (each formal seen from the receiver, for method calls, `new` and `super(...)`); everything else (receiver, operands, `==`, `instanceof`, conditions, indices, for-each, `var`) keeps `chequear`. With an expected type each branch must conform to it (`ERR_TERNARIO_RAMA_INCOMPATIBLE`) and the ternary returns the expected type, so the context's own conformance check never adds a second error; without one, the ternary takes the type of the branch the other conforms to, else `ERR_TERNARIO_INCOMPATIBLE` (no common supertype: two sibling classes are an error, unlike Java). The condition must be `boolean` and no branch may be void (`ERR_TERNARIO_RAMA_VOID`); all its errors go on the `?`. Classic locals and array initializers, when implemented, must pass the expected type too. For-each requires the expression to conform to `MiniIterable<T>`, a predefined interface registered in `TablaSimbolos.registrarMiniIterable()`. `Model/semantico/MiniIterable.java` only documents its shape, and the compiler doesn't use it.

`Tester{Sin,Con}ErroresSem2` and `resources/semantico2/` (`semIICorrectoNN`, `semIIErrorNN`) cover statement/expression checking. Sem2 error tags use the same `[Error:<lexema>|<línea>]` format, and they run on `ModuloPrincipalET4`. `TesterConErroresSem2` is stricter than the other error testers: the expected tag must be the **first** `[Error:...]` tag in the output. `TesterLogrosSem2` runs the logros listed in its `LOGROS_HABILITADOS` under `logros/`, requiring the output's `[Error:...]` tags to be exactly the leading `///[...]` tags, in order; enabling a new logro means adding its name there. The usage guide is `Documentación/testers/guia-testers-sem2.md`. `Documentación/etapa4-semantico2/casos-de-prueba.md` indexes every base case (rule § of the spec PDF it covers) and fixes the lexeme convention for Sem2 error tags.

Per-achievement cases (one folder per logro of `Documentación/etapa4-semantico2/requerimientos.md`) live in `Código/resources/semantico2/logros/<logro>/{conErrores,sinErrores}/`. The pending logros hold a skeleton (1 correct + 1 error case); the enabled ones have more: `for` 9 correct and 27 error cases (classic and for-each), `caminosRetornoSinCodigoMuerto` 9 + 21, `instanceOf` 4 + 15, `visibilidadChequeada` 4 + 11, `atributosInicializados` 5 + 16, `superKeyword` 10 + 37, `ternarios` 7 + 25, `multiDeteccionErrores` 1 + 4 (`postfijos` is still 1 + 1). Only the enabled logros are run by `TesterLogrosSem2`, and the expected lexemes of the others are provisional until their spec. `logros/` is a sibling of `sinErrores/conErrores` so the existing Sem2 testers don't pick it up.

## Design docs

`Documentación/` holds the reasoning behind the design. Read the relevant file before changing behaviour:
- `etapa2-sintactico/analizador-sintactico.md`: the grammar, how it was turned into LL(1), and FIRST/FOLLOW sets.
- `etapa3-semantico/analizador-semantico.md`: symbol table design, the two passes, the "Logros (Etapa 3)" requirements, and plans for statement checking (AST, `Entorno`).
- `etapa1-lexico/informe-analizador-lexico.md`: tokens and the REQ-* requirements.
- `testers/guia-testers-lexico.md`: how the testers work.
- `enunciados/`: the course spec PDFs. `Documentación/README.md` is the index.
